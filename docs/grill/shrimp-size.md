## Decisions
- **Stack (1 Nov):** Python FastAPI core serves a static web page (file input with capture, so no HTTPS needed), calls SAM, runs `decode.mjs` as a subprocess for masks, measures length in Python (spike code), rules and dashboard data in Python. Reason: one server, spike code reused, easy to test with synthetic masks. Rejected: keep the Werewolf stack's two servers (extra process for no demo gain); all TypeScript (port of the length algorithm costs day 1). Risk: two runtimes, Python 3.8.

- **Storage (1 Nov):** one SQLite file on the server (stdlib sqlite3), original photos beside it in a gitignored folder. Reason: phone and laptop share one history, easy to seed and test. Rejected: JSON file (concurrent writes, no queries by day); localStorage (one device only).
- **Demo data (1 Nov):** the photo taken live in the demo is real; the earlier history is seeded and labelled "demo data" on the dashboard and said so in the video. Reason: market shrimp cannot give real growth of one pond, and unlabelled numbers would cost trust. Rejected: several market batches over several days (each batch is a different lot, so the trend means nothing, and it costs effort); unlabelled synthetic data (misleading).
- **Old docs (1 Nov):** Werewolf spec, ledger, stack ADR and dev brief removed (git history keeps them); reusable Meta facts moved to `docs/meta-api.md`.
- **Error table (1 Nov):** 5 trays, about 50 shrimp, hand-measured with a ruler; the video states n. Charlie's choice, against my advice of 12 trays (about 120 shrimp). Risk: a small sample is easy to question; the answer is to say n and the limit. Rejected: 30 trays (3+ hours of measuring in the build window).
- **Stall threshold and harvest size (1 Nov):** default constants in one config file, editable on the setup page, labelled "assumption, not verified with a farmer". Starting values (mine, not from the farmer, to be tuned): stall when average length grew under 1 mm between samples 3 days apart; harvest size 50 per kg. Tests use these values; changing them changes no code. Rejected: wait for the first farmer (blocks the rules slice); show change only with no flag (loses the stall and cost feature).
- **Size per kg table (1 Nov):** a data file, replaceable. Until the CP table arrives, use a public length-weight table for whiteleg shrimp with its source written in the file, and show the label "temporary table, not the CP table" on screen. Rejected: weigh market shrimp to build the table (different species or frozen, not a pond); show length only (loses the size-per-kg message). Follow-up done: source found, see the size per kg source entry.
- **Schedule (1 Nov):** slice 0 (real photo to SAM to lengths on screen) and design-options on 1 Nov; rules, SQLite, input form, dashboard, demo data on 2 Nov; error table (5 trays) and fixes on 3 Nov with freeze that evening; video, README, submit on 4 Nov before 22:00. Cut order when late: Spark explanation, harvest flag, UI polish; never the error table. Rejected: freeze on 2 Nov (too little time for both features and the hand measuring); freeze on 4 Nov morning (video rushed).
- **Run and checks (defaults, two-way doors, 1 Nov):** the demo runs on the laptop, the phone opens it over the local network (a file input needs no HTTPS); checks are pytest and ruff, listed in `.agent/checks`.
- **Dashboard (1 Nov):** basic only: latest average length and size per kg, change since last sample, stall flag, cost of a stall day, one line chart, one table of samples (spec criterion 35). Reason: Charlie's choice; the second top feature stays small enough to finish on 2 Nov.
- **Spec approved (1 Nov):** by Charlie.

- **Review fixes (1 Nov, reviewer in spec mode):** stall rule is per day (0.33 mm per day, needs 5 measured shrimp in both samples); harvest flag added to the dashboard list; size table is rows with interpolation, looked up at the mean length; settings edited on the setup page are saved in SQLite over the config defaults; setup keeps only pond name, default feed price and reference size; the cost of a stall day is always shown; spike code copied into `spike/` because it only lived in a temp folder.
- **Length landmark (1 Nov, two-way door):** the app measures rostrum tip to telson tip, antennae excluded; the source paper measures postorbital edge to telson tip. The data file has a length factor, default 1.0 (unverified); hand-measure both landmarks on about 10 shrimp before the error table and set it. Rejected: assume the two are equal (a 5% longer length reads about 16% too heavy, so shrimp per kg is shown about 14% too low).
- **Size per kg source (1 Nov):** formula W = 1.3669e-5 * L^3.0077 (mm, g; unrounded constants, so the 100 mm value stays 71), fitted by the research agent from Chow and Sandifer 1991 cohort means, not printed by the authors; spread about 20% (Prajapati and Ujjania 2021 gives 11 to 20% lighter shrimp). No public CP or hatchery table found. See `docs/research/vannamei-length-weight.md`.

- **Prototype verdict (2 Nov, Charlie: "duyệt, làm theo ý tưởng của bạn"):** logic prototype of the dashboard rules (stall, harvest, cost, table lookup) clicked through on six scenarios. Settled: (a) the stall rule stays a strict "under 0.33 mm per day", so 1 mm over 3 days (0.333) is not a stall; (b) the stall flag stays a comparison of the last two samples, with N shown beside every sample, because tray means are noisy (a flat pond with a 2.5 mm swing in the mean makes the flag fire on noise and hide real stalls) and the video must not present the flag as a decision; rejected "two low samples in a row" (fewer false alarms but one sample later); (c) a mean length outside 60 to 140 mm still saves the sample, with an empty size and the notice `outside_table_range`; (d) editing the minimum shrimp count after saving makes the flag "cannot tell". The prototype stays in the scratchpad and is not committed.
- **Acceptance criteria (2 Nov):** 36 criteria approved by Charlie and written into the spec, replacing the first 11. Two proposals accepted with them: table range 60 to 140 mm and the same-day case (no stall flag, says "same day").
- **UI design (2 Nov, Charlie: "Dung design A"):** option A on all three screens from the design-options page: capture = one column (camera button, photo, Send, result stacked); input and setup = a Feed | Setup switch showing one short form at a time; dashboard = stacked cards in the spec's order. Reason: simplest to build in the time left. Rejected: B and C (more build time; the large status banner of dashboard B risks reading as advice).

- **Chat channel (2 Nov, Charlie's idea: "tích hợp vào Zalo hay Messenger, chatbot trả lời trực tiếp", because the web app looks bad and is hard to use):** the farmer sends the tray photo to a bot and gets the annotated photo and a few lines back. Q1 settled: Messenger for the demo (same Meta family, works with a developer/tester account without app review, needs a public HTTPS webhook), Zalo named as the next step (Zalo OA registration and approval for an individual are unverified, too risky in 2 days). Rejected: Zalo only, both channels, web-only redesign. Sources: Messenger Platform webhooks docs (developers.facebook.com), Official Rules page (`docs/meta-api.md`).
- **Choosing shrimp without a screen (2 Nov, Q2 settled):** automatic by default (current overlap rule plus a minimum length so fragments are dropped), the reply photo numbers every shrimp, the bot invites a text correction ("reply 1 3 5 to count only these"), and the tray instructions tell the farmer to lay shrimp apart. The server side of choosing (analysis id, include list) already exists; only the way in and out changes. Rejected: fully automatic with no correction (silent wrong numbers, no way to rescue a demo), a smarter "which shrimp is on top" rule (tip shape is ambiguous and there is no hand-measured truth to tune it), and dropping every touching shrimp (too few shrimp left).
- **What happens to the web page (2 Nov, Q3 settled):** the bot takes the photo and replies with the measured photo and a few lines plus a link to the dashboard. The web page stays as a read-only dashboard (design C, already built). The Photo screen goes away from the page; feed entry and setup stay on the web (the farmer rarely changes them). Rejected: chat-only (needs a new chart-image renderer, a command parser and removing tested code in 2 days) and keeping both full entrances (two ways to do one job, the current confusion).
- **Where the bot runs (2 Nov, Q4 settled, Charlie has an AWS account):** start on the laptop behind a Cloudflare quick tunnel to get the first end-to-end run today; move to a small EC2 instance behind CloudFront (a free `*.cloudfront.net` HTTPS address, no domain needed) before the freeze on the evening of 3 Nov. The API key lives only on the server, never in the repo. Charlie creates the AWS resources; the agent does not create cloud resources. Rejected: tunnel only (laptop off means bot off in front of the judges), AWS first (no demo until the server is built). Open: in Messenger development mode only app admins, developers and testers can message the bot, so judges cannot try it unless added as testers; the video is the proof.
- **Meta tooling in the bot (2 Nov, Q5 settled):** Muse Spark writes the Vietnamese reply from the structured result (numbers, flags, notices). Guards in code: every number in the reply must appear in the structured result, words that tell the farmer to harvest or sell are forbidden, and any Spark failure or violation falls back to a fixed template. Rejected for now: a Spark agent with tools and Voice Transcribe messages (highest score potential, most work; revisit only if time remains after the end-to-end run) and fixed templates only (SAM alone reads as "a simple image analyzer"). Open: Muse Spark price and access through the key are unverified.
- **Evidence for the accuracy work (2 Nov, measured):** on a 2048x1362 photo, the three long shrimp (161, 168, 173 mm) changed by about 1 to 2% at 1024 px and 4 to 6% at 720 px, but the tray mean moved between 84.5 and 104.7 mm across the four sizes because the set of small fragments counted changed. So the selection of shrimp matters more than the resolution; send the photo at 1024 px or more.
- **Fragments (2 Nov, Q6 settled):** a fixed minimum length of 50 mm by default (the size table starts at 60 mm, so shorter shrimp have no per-kg figure anyway), a setting editable on the Setup page; shrimp under it are listed as left out. Rejected: a ratio to the longest shrimp (drifts with small or mixed trays, hard to explain) and a shape filter (needs labelled data that does not exist yet).
- **When a sample is saved (2 Nov, Q7 settled, Charlie chose against the recommendation):** the bot replies with the result and asks "Save this sample? Reply Yes, or the numbers of the shrimp to count"; nothing is saved before the farmer confirms. This keeps the server's existing analyse-then-save flow. Cost: one more message per sample, and a sample not confirmed is lost. Rejected: auto-save with edit and cancel (needs new edit-sample and delete-sample operations on the server).
- **Two-way doors decided by the agent (2 Nov):** (1) the webhook answers 200 at once and does the SAM work in a background thread, because Messenger retries a slow webhook; repeated message ids are ignored; (2) every webhook call is checked with the app secret signature (X-Hub-Signature-256) and the verify token, and only allow-listed sender ids are served (the demo has one pond, so no accounts); (3) the server draws the reply photo itself (outlines, centre lines, a number and the length on each shrimp) from the same pixels the masks come from, which also removes the browser/EXIF coordinate risk of the old page; (4) the pending analysis of each sender is kept in memory with an expiry, like the analyses the service already keeps; (5) tests use a fake Messenger transport with real payload shapes, and one manual run with a real Page before the video. Cut order if time slips: Spark text (fixed templates instead), then the EC2 move (stay on the tunnel), then the text correction ("reply 1 3 5"). Not cut: the measured photo reply and the error table.
- **Out of scope for this pivot:** Zalo, voice messages and phone calls, several farmers or ponds, an agent with tools, auto-save.
- **Several ponds (2 Nov, Charlie asked how to set parameters for many ponds):** the build has one pond: samples, feed entries and every setting are shared, and the pond name in Setup is only a label. Decision for the submission: stay with one pond and say so in the README and the video. Roadmap, not built: ponds with their own name, stocking date, feed and thresholds; samples and feed entries belong to a pond; the bot picks the working pond with a command such as "ao 2"; the dashboard has a pond selector. Rejected for now: several ponds with their own settings (most of the work is the data model change) and several ponds with shared settings (two ponds of different age would share one threshold). Reason: two days left and the accuracy problems come first.

- **What the app can honestly claim (2 Nov, Charlie asked whether it solves "keep growing or harvest", and what else affects it; four research notes in `docs/research/`):** it does not decide keep-or-harvest and should not: sources treat harvest as an economic choice among target size, price by size, growth, survival, disease and weather risk, and the buyer (no source gives a hard growth cut-off). What it can do honestly: cheaper sampling, size and growth with their uncertainty (a handful of shrimp varies by a few mm: the standard error of the difference of two samples of 10 is about 3.6 mm against about 1 mm of growth in 3 days; FAO advises 50 to 100 shrimp a week), the value of the current size and how near the next price class is (price per kg falls fastest at the large end), and the feed-only break-even growth. Built: the spread of the samples and the "unclear" verdict (S16), the trend over the last four samples (S18), value by size and break-even (S19), merged blobs and crowded trays (S17). Known limits to state in the README and the video: no primary source for growth at 40 to 50 g, one study (n=30) for the length spread, derived numbers marked as derived, a default price table from one day's Tepbac board, one pond only.
- Rejected for now: more photos in one sample (the trend over several samples gives most of the gain without a new conversation state); a price override per farmer (the default table is labelled, the next step is to let the farmer type his price).
